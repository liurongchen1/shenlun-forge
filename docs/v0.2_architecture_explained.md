# shenlun-forge v0.2 架构讲解（大白话版）

> 这篇文档用通俗的方式解释框架在干什么，适合给别人讲的时候参考。

---

## 一句话说明白这东西干嘛的

**智能体聊天聊久了，上下文太长、LLM处理不过来，这东西帮你把没用的废话砍掉，只留关键信息。**

---

## 为什么需要它？

你用过 ChatGPT / 扣子 / Coze 这类智能体吧？聊了50轮之后：

- 上下文窗口快满了（LLM一次能吃掉的文字量是有限的）
- 前面聊的废话、重复内容占了大量空间
- 真正重要的决策、结论反而被"挤出去"了
- 智能体开始答非所问，或者忘了之前说的事

**传统方案的问题：**

| 方案 | 怎么做的 | 问题 |
|------|----------|------|
| 滑动窗口 | 只保留最近N条消息 | 重要但早期的内容直接丢了 |
| 全文摘要 | 把所有对话总结成一段话 | 细节丢失严重，代码/数字/决策容易丢 |
| RAG向量检索 | 用向量相似度找相关内容 | 找得不够准，且不能保证"完整性" |

**我们的方案：** 不是一刀切地丢，而是**像专家分析师一样，先搞懂你要问什么，再有针对性地保留相关信息**。

---

## 核心流程：四步走（申论方法论）

整个框架的设计灵感来自**申论考试的答题思路**——先看题，再找要点，然后整理合并，最后按格式写答案。

```
用户提问
    ↓
【第1步：审题】分析用户到底想知道什么
    ↓
【第2步：找要点】从历史对话中找出所有相关信息
    ↓
【第3步：整理合并】去重、打标签、合并同类项
    ↓
【第4步：按格式输出】在token预算内组装最终结果
    ↓
压缩后的上下文（喂给LLM）
```

### 用大白话解释每一步：

**第1步 ACSAnalyzer（审题）**

> "你说'数据库用什么方案'——那我需要找的是技术决策类信息，不是闲聊废话。"

这一步搞清楚：用户的问题属于什么类型（问答？分析？写代码？），需要保留哪些类型的关键要素（事实、数字、代码、决策……）。

**第2步 ACSRetriever（找要点）**

> "这50条对话里，跟数据库方案相关的有哪些？第3条说了用PostgreSQL，第17条说了密码加密方案——这两条要留。第5条'今天天气不错'——这条不要。"

给每条消息打一个"重要性分数"，分数高的留下，低的丢弃。评分标准根据第1步的结果来定——如果你问的是代码相关的事，代码段的分数就高。

**第3步 ACSProcessor（整理合并）**

> "第3条和第20条说的是一回事（都用PostgreSQL），合并成一条，别重复了。给这条打个标签叫'数据库技术选型'，以后好找。"

做三件事：
1. **去重**：同一个事说了多遍的，合并
2. **打标签**：给每块内容起个名字，方便检索
3. **规范化**：统一格式，比如时间统一成 YYYY-MM-DD

**第4步 ACSFormatter（按格式输出）**

> "token预算只剩4000了，最重要的信息优先放进去，放不下的就精简表达。最后组装成一段干干净净的文字。"

最终输出就是一段压缩后的文本，直接可以塞进LLM的上下文窗口。

## 三种压缩策略

框架不只有"一条路走到黑"的压缩方式，提供了三种策略：

### 1. Simple（简单粗暴型）

```
原文 → 按重要性排序 → 从最重要的开始往token预算里塞 → 塞不下就截断
```

**适合场景：** 快速压缩、对质量要求不高的场景
**特点：** 不调LLM、速度快、但可能丢掉上下文关联

### 2. ACS（四步精细型）

```
原文 → 审题 → 找要点 → 整理合并 → 按格式输出
```

**适合场景：** 需要高质量保留关键信息的场景
**特点：** 最精细，但需要调LLM做分析，有一定延迟

### 3. HCS（混合型，Hybrid）

```
先判断原文长短：
  - 短文本（<3000 tokens）→ 用Simple（快）
  - 长文本（≥3000 tokens）→ 用ACS（精细）
```

**适合场景：** 通用场景，自动选择最优策略
**特点：** 兼顾速度和质量

## 一个实际的例子

假设你和智能体聊了30轮关于一个Web项目的开发，然后问：

> "我们数据库和密码方案最终定了什么？"

**不压缩（原始30轮对话）：** 约 16000 tokens，LLM处理慢、费用高

**用 shenlun-forge 压缩后：** 约 4000 tokens（压缩率75%），内容大概是：

```
[技术选型] 数据库: PostgreSQL 16, 密码存储: bcrypt哈希, 
  会话管理: Redis + JWT

[安全决策] 
  - 弃用MD5: 安全团队评审确认抗碰撞性不足
  - Redis会话过期: 24小时, 敏感操作重新验证

[待确认] 
  - Redis主从切换时的会话保持方案
  - bcrypt cost factor是否需要调整(当前12)
```

关键信息全保留了，废话全砍了，token省了75%。

## 代码结构一览

```
shenlun_forge/
│
├── types.py          ← 数据结构定义（ContextBlock、TaskProfile等）
│                        相当于"词典"，定义框架里用到的所有概念
│
├── analyzer.py       ← 第1步：审题
│                        分析用户问题，确定需要保留什么
│
├── retriever.py      ← 第2步：找要点
│                        给每条消息打重要性分数，筛选相关内容
│
├── processor.py      ← 第3步：整理合并
│                        去重、打标签、合并同类信息
│
├── formatter.py      ← 第4步：按格式输出
│                        在token预算内组装最终文本
│
├── compressor.py     ← 主入口（ShenlunForge类）
│                        把四步串起来的"总指挥"
│
├── llm.py            ← LLM调用封装
│                        对接DeepSeek/OpenAI等模型API
│
├── base.py           ← 抽象接口定义
│                        定义每步"应该长什么样"，方便扩展
│
├── registry.py       ← 策略注册表
│                        管理Simple/ACS/HCS三种策略
│
└── strategies/       ← 三种策略的具体实现
    ├── simple.py     ← Simple策略
    ├── hybrid.py     ← HCS混合策略
    └── ...
```

**核心设计思路：每一步都是独立模块，可以单独替换。**

比如你不满意第2步的打分逻辑，可以只重写 `retriever.py`，其他步骤不用动。这就是为什么用"抽象接口 + 具体实现"的分层设计。

## 跟竞品比有什么优势？

| 维度 | 传统摘要 | RAG检索 | LangChain Memory | shenlun-forge |
|------|----------|---------|-----------------|---------------|
| 是否理解用户意图 | ❌ 无脑摘要 | ❌ 只看相似度 | ❌ 固定策略 | ✅ 先审题再压缩 |
| 代码/数字保留率 | 低 | 中 | 低 | 高（按信息类型加权） |
| 延迟 | 低 | 中 | 低 | 中（需调LLM分析） |
| 是否可插拔 | - | - | 部分 | ✅ 每步可独立替换 |
| 多策略支持 | ❌ | ❌ | 有限 | ✅ Simple/ACS/HCS |

**一句话总结：我们是唯一一个"先搞懂你要什么，再决定留什么"的压缩框架。**

## 使用示例（3行代码）

```python
from shenlun_forge import ShenlunForge

forge = ShenlunForge(model="deepseek-chat", api_key="your-key")

result = await forge.compress(
    messages=[...],          # 你的对话历史
    current_query="数据库用的什么方案？",  # 用户当前问题
    max_tokens=4000,         # token预算
)

print(result.compressed_text)  # 压缩后的干净文本
```

就这么简单。内部的四步管线全自动，使用者不需要关心。

## 一句话总结

> shenlun-forge 就是一个"智能体的记忆管理器"——智能体聊多了记不住事，它帮你把该记的记下来、不该记的扔掉，而且是**根据你当前要问的问题来决定该记什么**，不是无脑地全留或全删。
