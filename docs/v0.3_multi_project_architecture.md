# shenlun-forge v0.3 架构设计方案

## 多项目上下文隔离与智能路由

> 从"单上下文压缩"到"多项目隔离压缩"

---

## 1. 问题陈述

当前智能体（Coze/扣子、ChatGPT、Claude 等）在处理多项目并行时存在系统性缺陷：

```
用户：项目A的数据库设计我们用什么方案来着？
智能体：[加载了项目A和项目B的混合上下文]
回答：你们用 PostgreSQL 和 Redis……（其中 Redis 是项目B的）
```

根本原因是**单一上下文窗口**——所有对话历史、记忆、项目信息混在一个扁平列表里。当项目数量增多，上下文相互"污染"，表现为：

| 症状 | 本质 |
|------|------|
| 记忆混淆 | 项目A的决策被当作项目B的上下文 |
| 话题漂移 | 聊着项目A，智能体突然跳到项目B的细节 |
| 上下文溢出 | 多项目信息叠加，快速耗尽窗口 |
| 压缩失效 | 现有压缩不区分归属，关键信息被误删 |

现有压缩框架（包括 shenlun-forge v0.2）解决的是"单项目上下文太长"的问题，但没有解决"多项目上下文混在一起"的问题。

---

## 2. 核心思路

在现有压缩管线之前，加一层**语义路由层**：

```
当前 v0.2:
  messages → 语义评分 → 压缩 → 输出

新增 v0.3:
  messages → 项目分类 → 按项目隔离 → 分别压缩 → 结构化输出
```

不替换现有压缩能力，而是在其上游增加隔离。每个项目拥有独立的上下文实例，压缩互不干扰。

## 3. 新增数据模型

### 3.1 Project（项目）

```python
@dataclass
class Project:
    """一个独立的项目/话题上下文单元"""
    id: str                        # UUID
    name: str                      # "GEO广告智能体" / "北邮自考" / ...
    description: str = ""          # 一句话描述，用于语义匹配
    keywords: list[str] = []       # 关键术语，辅助分类
    created_at: float = 0.0
    last_active: float = 0.0
    message_count: int = 0
    
    def matches_topic(self, text: str) -> float:
        """计算文本与本项目的语义相关度（0-1）"""
        ...
```

### 3.2 ProjectContext（多项目上下文容器）

```python
@dataclass
class ProjectContext:
    """多项目隔离上下文"""
    projects: dict[str, Project] = {}
    # 每个项目独立的 ContextBlock 列表
    messages_by_project: dict[str, list[ContextBlock]] = {}
    # 分类器的内部状态（用于话题漂移检测）
    _classifier_state: dict = {}
    
    def add_message(self, block: ContextBlock, project_id: str):
        """将消息归入指定项目"""
        ...
    
    def get_project_context(self, project_id: str) -> list[ContextBlock]:
        """获取单个项目的完整上下文（用于传入压缩管线）"""
        ...
    
    def create_project(self, name: str, **kwargs) -> Project:
        """创建新项目"""
        ...
```

### 3.3 RoutedCompressionResult（路由压缩结果）

```python
@dataclass  
class RoutedCompressionResult:
    """多项目隔离压缩的最终输出"""
    # 每个项目的独立压缩结果
    by_project: dict[str, CompressionResult] = {}
    # 汇总统计
    total_original_tokens: int = 0
    total_compressed_tokens: int = 0
    # 路由决策日志（调试用）
    routing_log: list[dict] = []
    
    def to_structured_text(self) -> str:
        """输出结构化文本，供下游 LLM 使用"""
        # 输出格式：
        # [Project: GEO广告智能体]
        #   compressed_context...
        # [Project: 北邮自考]  
        #   compressed_context...
        ...
```

## 4. 核心组件设计

### 4.1 ProjectRouter（语义路由器）

负责把每条消息分配到正确的现有项目，或判断需要创建新项目。

```
输入: 新消息 + 现有项目列表
输出: 路由决策 (归属哪个项目 / 新建项目)
```

**分类策略（三级降级）：**

```
Level 1: 关键词匹配（快，无需 LLM）
    新项目关键词命中 → 直接路由
    例：用户说"自考报名时间" → 命中"北邮自考"项目的 keywords

Level 2: 语义相似度（中速，用 embedding）
    计算消息与各项目描述的 embedding 相似度
    最高相似度 > 阈值(0.75) → 路由到该项目
    所有项目相似度 < 阈值 → 触发新项目检测

Level 3: LLM 分类（慢，但最准）
    构造 prompt：
    "以下消息属于哪个项目？如果没有匹配项目，返回 NEW。"
    可选：当 Level 2 不确定时降级到这里
```

**话题漂移检测：**

维护一个"最近N条消息的主要项目"滑动窗口。如果连续3条消息都指向项目B，即使中间穿插了项目A的提问，也触发项目切换。

```python
class TopicDriftDetector:
    """检测话题是否发生切换"""
    window_size: int = 5
    history: list[str] = []  # 最近消息的 project_id
    
    def update(self, project_id: str) -> str:
        self.history.append(project_id)
        if len(self.history) > self.window_size:
            self.history.pop(0)
        # 如果最近3条都指向新项目 → 确认切换
        ...
```

### 4.2 ProjectManager（项目生命周期管理）

```python
class ProjectManager:
    """管理项目的创建、合并、归档"""
    
    def create_project(self, name: str, initial_keywords: list[str] = None) -> Project:
        """创建新项目，可选 LLM 自动生成关键词"""
        ...
    
    def merge_projects(self, from_id: str, to_id: str):
        """合并两个被误分类为不同项目的上下文（用户手动触发）"""
        ...
    
    def archive_project(self, project_id: str):
        """归档不活跃项目（超过30天无消息），释放内存"""
        ...
    
    def list_active_projects(self) -> list[Project]:
        """返回当前活跃项目列表"""
        ...
    
    def export_project(self, project_id: str) -> dict:
        """导出单个项目的完整上下文（用于持久化或迁移）"""
        ...
    
    def load_project(self, data: dict) -> Project:
        """从持久化存储加载项目"""
        ...
```

### 4.3 IsolatedCompressor（隔离压缩器）

在现有 ACSCompressor 基础上封装，核心逻辑不变，只是"每个项目单独调一次"：

```python
class IsolatedCompressor:
    """对每个项目独立执行压缩"""
    
    def __init__(self, base_compressor: ACSCompressor):
        self._compressor = base_compressor
    
    def compress_all(self, project_context: ProjectContext, 
                     task_profile: TaskProfile = None) -> RoutedCompressionResult:
        """对所有活跃项目分别压缩"""
        result = RoutedCompressionResult()
        
        for project_id, blocks in project_context.messages_by_project.items():
            # 把该项目的 blocks 打包成单个 context_text
            context_text = self._blocks_to_text(blocks)
            
            # 调用现有压缩管线（完全不改动）
            compressed = self._compressor.compress(
                context_text=context_text,
                task_profile=task_profile
            )
            
            result.by_project[project_id] = compressed
        
        return result
```

## 5. 整体管线

```
用户发送消息
      │
      ▼
 [ProjectRouter]
 消息属于哪个项目？
      │
      ├──→ 匹配到 Project A
      │        ↓
      │   [Project A 的 ContextBlocks]
      │        ↓
      │   [ACSAnalyzer - 语义评分]
      │        ↓
      │   [ACSScorer - 重要性评分]
      │        ↓
      │   [ACSCompressor - 压缩]
      │        ↓
      │   输出: Project A 的压缩上下文
      │
      ├──→ 匹配到 Project B（同理）
      │
      └──→ 新项目（创建 Project C，从这条消息开始积累）
```

**关键设计原则：**

1. **压缩管线不变**：每个项目内部的压缩逻辑完全复用现有 ACS 管线，不引入新的压缩算法
2. **隔离是核心**：不同项目的 ContextBlocks 永远不混合，压缩互不干扰
3. **路由在上游**：先分类再压缩，而不是压缩后分类
4. **可选结构化输出**：下游 LLM 可以选择只看到当前项目的上下文，也可以看到所有项目的摘要

## 6. 下游集成方式

压缩完成后，输出给下游 LLM 的格式有几种选择：

### 模式 A：当前项目模式（推荐默认）

只把用户当前讨论项目的压缩上下文传给 LLM，其他项目完全不可见。

```
[System Prompt]
You are an assistant helping with the current project.

[Compressed Context - Project A only]
...

[User Message]
...
```

优点：上下文最纯净，不会串味。
缺点：如果用户说"参考之前那个项目的设计"，需要手动切换。

### 模式 B：全项目摘要模式

把所有项目的压缩摘要都放进去，当前项目给完整上下文，其他项目只给一行摘要。

```
[System Prompt]
You are managing multiple projects. Current active: [Project A]

[Current Project A - Full Compressed Context]
...

[Other Projects - Summary Only]
- Project B: 北邮自考备考中，8月30日报名，10月考试...
- Project C: 衣尚AI穿搭网站，Vue3+FastAPI，已上线测试...

[User Message]
...
```

优点：跨项目引用时能知道有其他项目的存在。
缺点：摘要占用 token。

### 模式 C：显式引用模式

默认用模式 A，当用户说"参考项目B"时，动态拉取项目B的压缩上下文注入。

```
[触发] 用户说："参考一下项目B的数据库设计"
[动作] 拉取 Project B 的压缩上下文，临时注入
```

## 7. 存储与持久化

### 方案：文件系统存储（轻量，无需外部依赖）

```
shenlun_forge_workspace/
├── projects/
│   ├── {project_id_1}.json    # 项目元数据 + keywords + description
│   ├── {project_id_2}.json
│   └── ...
├── contexts/
│   ├── {project_id_1}/        # 每个项目独立目录
│   │   ├── messages.json      # 原始消息 ContextBlocks
│   │   └── compressed.json    # 最近一次压缩结果
│   └── {project_id_2}/
│       ├── messages.json
│       └── compressed.json
└── router_state.json          # 路由器的内部状态（分类器参数等）
```

优点：
- 零依赖，纯文件操作
- 项目之间完全物理隔离
- 易于备份、迁移、版本控制

### 可选：SQLite 存储（中量级）

如果消息量很大（10000+条/项目），换用 SQLite，按 project_id 分表。

## 8. 技术难点与方案

### 8.1 分类准确率问题

| 场景 | 难点 | 方案 |
|------|------|------|
| 用户明确切换 | "换个事" / "另一个项目" | 关键词触发，直接切换，高准确率 |
| 话题渐变 | 聊着A，慢慢偏向B | 滑动窗口检测，连续N条归属B则切换 |
| 跨项目引用 | "参考项目A的做法来做B" | 识别为跨项目，临时注入A的上下文 |
| 全新话题 | 没有关键词命中 | LLM fallback 判断是否新建项目 |

### 8.2 分类成本问题

每调一次 LLM 分类都有 token 开销和延迟。

**分级策略控制成本：**

```
Level 1 关键词匹配: ~0ms, 0 cost       → 覆盖 60% 的消息
Level 2 embedding:  ~50ms, ~0 cost     → 覆盖 30% 的消息  
Level 3 LLM:        ~500ms, ~0.01元/条 → 覆盖 10% 的消息
```

90%的消息不需要调 LLM，成本可控。

### 8.3 用户确认 vs 全自动

完全自动有风险：分类错了，用户说的项目B的内容被归到项目A，然后永远找不回来。

**推荐方案：自动分类 + 轻量确认**

- 高置信度（>0.85）：直接路由，不打扰用户
- 中置信度（0.6-0.85）：路由到最可能的项目，但在输出中提示"已归入Project X，如需修改请说'这不是项目X'"
- 低置信度（<0.6）：明确询问"这条消息属于哪个项目？还是新建一个？"

## 10. 实施阶段

### Phase 1: 基础路由（v0.3.0-alpha）

- 新增 `Project` 和 `ProjectContext` 数据模型
- 实现 Level 1 关键词分类器
- 实现项目隔离存储（文件系统）
- 暴露 `IsolatedCompressor` API

**验证标准：** 手动指定项目ID，验证两个项目的上下文完全隔离、压缩结果互不影响。

### Phase 2: 智能分类（v0.3.0-beta）

- 实现 Level 2 embedding 语义相似度分类
- 实现话题漂移检测器
- 添加自动创建新项目的逻辑

**验证标准：** 给定多项目混合对话，自动分类准确率 > 80%。

### Phase 3: 结构化输出 + 持久化（v0.3.0-rc）

- 实现三种下游集成模式（A/B/C）
- 实现项目持久化（JSON存储）
- 添加 `list_projects` / `switch_project` 命令

### Phase 4: 完整产品化（v0.3.0）

- LLM fallback 分类器（Level 3）
- 用户确认交互协议
- 完整文档和示例

## 11. 开放问题

以下几点需要讨论确认，影响架构走向：

### Q1：分类器依赖的 embedding 模型用什么？

- 选项A：sentence-transformers（本地，需下载模型，~300MB）
- 选项B：直接用 LLM 的 embedding 接口（已有 OpenAI/DeepSeek 依赖）
- 选项C：纯 LLM 分类，不用 embedding

### Q2：项目边界的定义粒度？

- "一个项目"是指一个代码仓库？一个业务目标？还是一段连续对话？
- 粒度太粗：多个子项目还是混在一起
- 粒度太细：分类器负担重，用户管理成本高

### Q3：是否需要支持"项目内子话题"？

比如项目A内部还有"数据库设计"、"前端UI"、"部署方案"三个子话题，是否也要隔离？

### Q4：与 Agent 框架的集成形态？

- 作为独立 Python 库，Agent 框架调用它的 API？
- 作为 Agent 框架的内部模块，深度集成？
- 作为中间件/适配器，兼容 LangChain / Coze / AutoGen 等？
