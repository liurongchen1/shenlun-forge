# v0.3 框架优化方案：12个改动项 × 性能预估

> 基于 v0.2.1 SOTA 实验数据（6场景69个事实点），预估每项改动对事实保留率的影响

---

## 当前基线（v0.2.1）

| 场景 | 总事实数 | 当前保留率 | 当前压缩率 |
|------|---------|-----------|-----------|
| Fact Recall | 16 | 15/16 (93.8%) | 75.6% |
| Code Detail | 10 | 1/10 (10.0%) | 75.6% |
| Architecture | 15 | 13/15 (86.7%) | 75.6% |
| Tasks/Timeline | 10 | 2/10 (20.0%) | 75.6% |
| Security Analysis | 10 | 8/10 (80.0%) | 75.6% |
| Rejected Alternatives | 8 | 8/8 (100%) | 75.6% |
| **全局平均** | **69** | **47/69 (68.1%)** | **75.6%** |

**两个致命短板：**
- Code Detail：10%——代码细节几乎全丢
- Tasks/Timeline：20%——时间线和任务序列保留极差

## 改动方案与性能预估

### 第一批：P0 + P1（基础设施 + 核心创新）

#### P0: TaskProfile 新增字段
- **改动**：types.py 加 `classification_dimension` 和 `output_logic` 两个字段
- **改动量**：20行代码
- **直接性能影响**：0%（纯基础设施，不改评分逻辑）
- **间接影响**：解锁 P1/P9-P11 所有下游改进
- **风险**：零，默认值 `auto` 保持原行为

#### P1: Analyzer 信号二（query关键词 → 分类维度）
- **改动**：analyzer.py 加 DIMENSION_KEYWORDS 字典 + 关键词匹配逻辑
- **改动量**：约50行代码
- **性能影响**：

| 场景 | 当前 | 预估 | 变化原因 |
|------|------|------|---------|
| Tasks/Timeline | 20% | 35-40% | "流程/步骤/阶段"关键词→process维度→按时间线组织输出 |
| Security Analysis | 80% | 85% | "原因/根源"关键词→layer维度→深层分析优先 |
| 其他 | — | +2-3% | 分类维度让下游Retriever/Formatter更精准 |

**预估全局提升：+3~5%**

---

### 第二批：P2-P5（Retriever 四因子增强）

这四个改动都是给 Retriever 的评分函数加新因子，互相独立，可以一起改。

#### P2: 首尾位置加权
- **逻辑**：前20%和后20%的block额外+0.05分
- **影响场景**：Fact Recall（开头通常包含关键事实定义）
- **预估提升**：Fact Recall 93.8%→95%，全局 +0.5%

#### P3: 词频特征加权
- **逻辑**：与query重叠且在block中出现≥2次的词，每个+0.03分（上限0.10）
- **影响场景**：Architecture（反复出现的架构概念被加强）
- **预估提升**：Architecture 86.7%→90%，全局 +1%

#### P4: 来源权威性加权
- **逻辑**：检测"确认/决策/必须/规定"等权威信号词，每个+0.05分（上限0.15）
- **影响场景**：Security Analysis（安全决策类信息权重提升）
- **预估提升**：Security 80%→85%，全局 +0.5%

#### P5: 结构层次检测
- **逻辑**：深层分析词汇+0.08，表层现象词汇-0.03
- **影响场景**：Tasks/Timeline（深层原因被优先保留）
- **预估提升**：全局 +0.5%

**P2-P5 合计预估提升：+2.5~3.5%**

> 注意：每个因子单独看都很小（0.03-0.15分），但它们是加在评分边界上的——
> 那些"刚好被过滤掉"或"刚好被保留"的block，加一点分就可能翻转结果。
> 参考Kahneman：多因子融合 > 单一判断。

---

### 第三批：P6-P8（Processor 质量增强）

#### P6: 共性问题/个性问题识别
- **逻辑**：跨block重复出现≥3次的标注为"common"，只出现1次的标注为"unique"
- **影响**：共性信息（跨主题重复的核心概念）被优先保留
- **预估提升**：Fact Recall +1%，全局 +0.5%

#### P7: 因果链组装
- **逻辑**：PROBLEM→ACTION→EFFECT 连续block标注因果链关系
- **影响场景**：Security Analysis（问题→对策→效果链完整保留）
- **预估提升**：Security 85%→90%，Tasks/Timeline 35%→45%，全局 +1.5%

#### P8: 三标准质量检查
- **逻辑**：过滤掉无source_trace、过短（<50字符）、内容重复的block
- **影响**：防止输出退化，但不直接增加保留率
- **预估提升**：全局 +0.5%（防止退化）

**P6-P8 合计预估提升：+2~3%**

---

### 第四批：P9-P11（Formatter 结构化输出）

#### P9: output_logic 处理（并列/因果/递进）
- **逻辑**：根据 output_logic 选择不同的block排序策略
- **影响场景**：Tasks/Timeline（递进式输出按时间排列）、Security（因果式输出按问题→对策排列）
- **预估提升**：Tasks/Timeline 45%→55%，全局 +2%

#### P10: 分类维度分组
- **逻辑**：根据 classification_dimension 选择不同的分组策略
- **影响场景**：Architecture（按领域/要素分组更清晰）
- **预估提升**：Architecture 90%→93%，全局 +1%

#### P11: 输出头部标注
- **逻辑**：输出开头加一行分类维度标识
- **影响**：对LLM理解压缩结果有辅助作用
- **预估提升**：全局 +0.3%（间接提升下游LLM准确率）

**P9-P11 合计预估提升：+3~3.5%**

### 额外项：针对 Code Detail 的专项修复

现有12个改动项**没有一个能解决 Code Detail 10%的问题**。需要单独加：

#### P-Code: 代码去脂肪 + 跨消息去重

**核心思路**：不需要 AST 解析，不用花哨编码。代码块当代码保留，只去掉"脂肪"；同一段代码出现多次只存一份。

**第一步：代码去脂肪（单块内压缩）**

对检测到的代码块（```包裹、含 `def `/`class `/`function ` 等特征），执行纯正则清洗：
- 删除空行
- 删除单行注释（`#`、`//`）
- 删除多行注释/文档字符串（`"""..."""`、`/*...*/`）
- 保留缩进结构不变（Python 依赖缩进）
- 保留所有代码逻辑、变量名、函数签名完整不动

效果示例：
```python
# 去脂前（42 tokens）
def calculate_total(price, tax_rate=0.1):
    """
    Calculate total with tax.
    Args:
        price: base price
    """

    subtotal = price * (1 - discount)

    tax = subtotal * tax_rate

    return subtotal + tax

# 去脂后（22 tokens，节省约 48%）
def calculate_total(price, tax_rate=0.1):
    subtotal = price * (1 - discount)
    tax = subtotal * tax_rate
    return subtotal + tax
```

**为什么不用二进制/编码方案：**
LLM 训练的语料就是源代码文本，它最擅长读的就是代码原文。Base64 反而增加 token 量，二进制 LLM 看不懂，JSON AST 信息全在但 token 更多。**去脂肪是唯一既省 token 又零信息损失的方案。**

**第二步：跨消息代码去重**

多轮对话中同一段代码经常反复出现（改了又改、引用了又引用）。策略：
- 对每个代码块计算内容哈希（去脂后）
- 首次出现：完整保留
- 后续出现：替换为引用标记 `[代码引用: #1, 见上方 {函数名/文件名}]`
- 引用标记只占几个 token，但 LLM 能回溯理解

**预估提升**：
- Code Detail：10% → 45-55%（代码不再被截断丢失）
- 其他场景：代码相关 block 的 token 体积减小 30-50%，间接释放 token 预算给非代码内容
- 全局：+3~5%

## 风险和不确定性

1. **预估值可能偏乐观**：每个因子独立看都有道理，但组合起来可能有非线性效应（互相干扰）
2. **Code Detail 是最难啃的骨头**：去脂肪+去重方案实现简单，但 45-55% 的上限取决于代码块在总 token 中的占比；如果代码块本身被截断而非仅压缩，提升可能更显著
3. **Tasks/Timeline 提升空间大但不确定性也大**：从 20% 到 60% 需要 P1+P7+P9 三个改动协同生效
4. **LLM 非确定性**：实验结果受 LLM 输出随机性影响，单次实验数据可能波动
5. **压缩率可能下降**：保留更多事实意味着压缩率可能从 75.6% 降到 70-72%
